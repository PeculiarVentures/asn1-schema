# Contributing to asn1-schema

Thank you for your interest in contributing to `asn1-schema`! This document describes how to set up the project, which checks a change must pass, how to add a package, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)

### Installation

```bash
git clone https://github.com/PeculiarVentures/asn1-schema.git
cd asn1-schema
npm ci
npm test
npm run build
```

## Project Layout

- `packages/<name>/` is the `@peculiar/asn1-<name>` package (`packages/schema/` is `@peculiar/asn1-schema`, the decorators, parser, serializer and schema storage the other packages build on).
- `packages/<name>/src/index.ts` is the package's only public entry point and must stay aligned with its `exports`.
- `tsdown.config.ts` at the repository root builds every package (tsdown `workspace` mode). There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking, tests and the declaration build. Its `paths` map every `@peculiar/asn1-*` package to its `src`, so packages and tests use the sibling sources without building them first.
- `packages/<name>/build/` is generated by `npm run build` and is not committed.

## Development Workflow

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks every package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, and `npx vitest run packages/<name>` to run one package's tests.

### Testing

- Use Vitest: import `describe`, `it` and `expect` from `vitest` (globals are off) and assert with `expect`, not `node:assert`.
- Put tests next to the code they cover as `*.spec.ts` (module tests in `packages/<name>/src/`, public-API tests in `packages/<name>/src/index.spec.ts`).
- Cover new behavior and bug fixes with tests. For parsing or serialization changes, check the exact decoded values, the serialized bytes, or a round trip.
- Keep tests deterministic: no wall-clock time, randomness, network access or external services.

### Build And Package Exports

Every package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations. Output is unbundled, so every source module is emitted under `build/` mirroring `src/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in each `packages/<name>/package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the packages keeps working on supported Node.js versions. Use `import type` for type-only imports (`verbatimModuleSyntax`).

Every package has `"sideEffects": false`. The decorators register a schema when the module that declares the class runs, and parsing or serializing needs that class at runtime, so bundlers keep the module. Don't add code that only works because some other module was imported for its side effects.

### Dependencies

- `@peculiar/asn1-schema` is a **peer** dependency (and a dev dependency) of every other package: the decorators register into the storage of one asn1-schema copy, so an app must have only one.
- `asn1js` is a **peer** dependency (and a dev dependency) of every package that imports it, because asn1-schema checks `instanceof asn1js.*`.
- Other `@peculiar/asn1-*` packages and `@peculiar/utils` are regular `dependencies`. Use the `@peculiar/utils` root or subpath entries (`/bytes`, `/encoding`), never `/legacy`.
- Internal `@peculiar/asn1-*` ranges are bumped by the release pull request; don't change them by hand.

### Adding A Package

```bash
npm run create <name>
npm install
npm run build
```

This creates `packages/<name>` (`package.json`, `README.md`, `LICENSE`, `src/index.ts`) as `@peculiar/asn1-<name>` at the current version and adds it to the `paths` in `tsconfig.json`. The build and the release flow pick it up automatically. Before the first release, configure its npm Trusted Publisher (see [Releases](#releases)).

Keep the package README short and factual, following the other `packages/*/README.md`: the package name as the heading, the license and npm badges, a one-sentence description (for schema modules, mention the `@peculiar/asn1-schema` helpers `AsnConvert`, `AsnParser` and `AsnSerializer`), an `Installation` section with the exact `npm install` command, and a `Specifications`, `References` or `Overview` section linking the RFC or standard. Add a short example only when it helps explain the API.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the package directory as the scope for package-specific changes (for example `fix(x509): ...`, `feat(schema): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(schema)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `master`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration. Keep the lint config practical: prefer fixing the source over adding rules that only create churn, and disable a rule only when it fights the established style.
- Keep changes small and localized to the owning package.
- Prefer `BufferSource`-based public APIs over Node.js-specific `Buffer` types.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). All packages share one version and are released together.

1. On every push to `master`, the **Release** workflow first runs lint, format, typecheck, tests, and build (the **Test** workflow). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and every `packages/*/package.json` version, the internal `@peculiar/asn1-*` ranges, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release. Any releasable commit releases every package, including commits that only touch root files.
2. Merge the release pull request. release-please creates one `vX.Y.Z` tag and one GitHub Release with the notes from the pull request; the workflow then publishes every package whose version is not on npm yet via Trusted Publisher, with provenance, dependencies first, and moves the major tag (for example `v3`) when this is the newest release of that major.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Every package needs an npm Trusted Publisher for this repository, workflow `release.yml` and environment `npm`; a new package must be published once and configured before its first automated release.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/asn1-schema/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
